WebSpaces

Containers

A container is a tab group with its own cookie vault. A named group you create in Chrome becomes a container on its own, and renaming or recolouring either side carries over to the other.

Opening rules

An address matching a pattern goes to the given container without asking, including addresses on hosts that belong to no realm. A new rule also covers tabs already open.

A bare host means the whole site, subdomains included: example.com also catches www.example.com. You can paste an address straight from the address bar, since https:// and a trailing slash are ignored. A star stands for any fragment (*.sharepoint.com), and a slash narrows the rule to a path (admin.microsoft.com/*).

Isolation realms

A realm is a set of hosts whose cookies collide between containers. Only those are swapped, so hosts outside every realm work normally and are never frozen. The realms below are a starting point: edit them, delete them, add your own.

List only hosts shared across organisations, where cookies actually collide (id.atlassian.com, login.microsoftonline.com). Addresses whose name carries the organisation (acme.atlassian.net, acme.sharepoint.com) belong outside the realm, because they do not collide and can run in several containers at once.

Behaviour

Backup & Sync

Uploads containers, realms, rules, windows and tabs into a WebSpaces folder on the Drive of the account signed into this Chrome profile. Cookies never go there: the file lands in the cloud unattended, and sign-in sessions in plain text would open every tenant to anyone who takes over that Google account.

Setup

Google requires every application to be registered before it can touch a Drive. This takes about five minutes and only has to be done once. Each step opens the page you need in a new tab.

Signing into Google Cloud goes through accounts.google.com, which sits in your Google realm. If the container picker appears, choose the container holding the Google account you want to use for backups.
  1. 1Copy the extension ID

    Google ties the credentials to this exact extension. The ID depends on the folder the extension is loaded from, so it changes if you move the project.

  2. 2Create a Google Cloud project

    A project is just a container for the credentials. Any name will do and nothing is billed.

    Open project creation
  3. 3Enable the Google Drive API

    Press Enable on the page that opens. Without this the credentials exist but every call is refused.

    Open the Drive API page
  4. 4Configure the consent screen

    Choose External (or Internal on Workspace), add the scope .../auth/drive.file and add your own address as a test user. That scope is the narrowest one available: the extension sees only files it created itself and cannot read the rest of your Drive.

    Open the consent screen
  5. 5Create the OAuth client

    Create credentials, pick the application type Chrome Extension, and paste the ID from step 1. Copy the client ID it gives you back.

    Open credentials
  6. 6Put the client ID into the build

    The client ID is private to your installation, so it is never committed. Save it in google-client-id.txt in the project root, rebuild, then reload the extension at chrome://extensions.

    npm run build

  7. 7Connect and upload

    Chrome asks for consent once, using the account already signed into this profile. No sign-in page is opened, so nothing lands in the cookie jar and the isolation gate has nothing to intercept.
