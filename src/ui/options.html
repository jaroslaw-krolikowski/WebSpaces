WebSpaces

Containers

A container is a tab group with its own cookie vault. A named group you create in Chrome becomes a container on its own, and renaming or recolouring either side carries over to the other.

Opening rules

An address matching a pattern goes to the given container without asking, including addresses on hosts that belong to no realm. A new rule also covers tabs already open.

A bare host means the whole site, subdomains included: example.com also catches www.example.com. You can paste an address straight from the address bar, since https:// and a trailing slash are ignored. A star stands for any fragment (*.sharepoint.com), and a slash narrows the rule to a path (admin.microsoft.com/*).

Isolation realms

A realm is a set of hosts whose cookies collide between containers. Only those are swapped, so hosts outside every realm work normally and are never frozen. The realms below are a starting point: edit them, delete them, add your own.

List only hosts shared across organisations, where cookies actually collide (id.atlassian.com, login.microsoftonline.com). Addresses whose name carries the organisation (acme.atlassian.net, acme.sharepoint.com) belong outside the realm, because they do not collide and can run in several containers at once.

Behaviour

Backup & Sync

Uploads containers, realms, rules, windows and tabs into a WebSpaces folder on the Drive of the account signed into this Chrome profile. Cookies never go there: the file lands in the cloud unattended, and sign-in sessions in plain text would open every tenant to anyone who takes over that Google account.

Setup

Google has no registration-free way into a Drive: every call needs a client ID, and a client ID needs a Cloud Console project. You register your own, so the access runs under your project and your quota and nobody else is responsible for it. It takes about five minutes and is done once. Each step opens the page it needs in a new tab.

Signing into Google Cloud goes through accounts.google.com, which sits in your Google realm. If the container picker appears, choose the container holding the Google account you want to use for backups.
  1. 1Copy the extension ID

    Google ties the credentials to this exact extension. By default the ID is derived from the folder the extension loads from, so it changes if you move the project and differs on another machine. Running npm run key once pins it for good, which keeps a single registration valid everywhere.

  2. 2Create a Google Cloud project

    A project is just a container for the credentials. Any name will do and nothing is billed.

    Open project creation
  3. 3Enable the Google Drive API

    Press Enable on the page that opens. Without this the credentials exist but every call is refused.

    Open the Drive API page
  4. 4Configure the consent screen

    Choose External (or Internal on Workspace) and add the scope .../auth/drive.file. It is the narrowest one available: the extension sees only files it created itself and cannot read the rest of your Drive.

    Then press Publish app on the Audience page. Left in Testing, the consent screen refuses every account that is not on the test user list, which is the usual cause of Error 403: access_denied - and refresh tokens issued in Testing expire after seven days, so unattended uploads would quietly stop every week. Publishing needs no review here, because drive.file is a non-sensitive scope.

    Open scopes Open audience and publishing
  5. 5Create the OAuth client

    Create credentials and pick the application type Web application. Add the address below as an authorised redirect URI, then copy both the client ID and the client secret it hands back.

    Not the Chrome Extension type. That one issues no client secret, and Google will not return a refresh token without one, so unattended uploads would stop working after an hour. If you already made a Chrome Extension client, leave it and create a Web application client next to it.

    Open credentials
  6. 6Paste the credentials

    Google shows both right after the client is created, and again on the client page under Additional information. Only a Web application client has a secret; if the field is missing, go back to step 5 and check the application type.

    They are stored on this device only and never reach the configuration sync, the backup file, or the repository. For an installed application the secret is not a real secret: it identifies the project, it does not protect it.

  7. 7Connect and upload

    A Google consent window opens once. WebSpaces lifts its own network gate for those few seconds, otherwise the sign-in page would be redirected to the container picker and the flow could never finish.

    The sign-in also writes Google cookies into whichever container is mounted right now. That is harmless afterwards, since the stored refresh token is what keeps uploads working, but it is worth knowing where those cookies landed.
